## 0. Как работать с этим ТЗ в Codex

1. Найти в репозитории текущий раздел **«Условия финансирования»**: маршруты, сущности, API калькулятора, создание заявки, карточка партнёра.

3. Сначала миграция данных и серверные правила, затем API, затем UI.
4. Покрыть автотестами алгоритм ставки, режимы применения базовой ставки, права ролей, снимок заявки.
5. Не удалять использованные программы. Только деактивация.
6. Не давать партнёру API изменения ставки, даже если UI это скрывает.
7. Если в коде уже есть «копия условий на партнёра» — заменить ссылкой на программу + таблицей исключений.

Запрещённые решения:

- отдельная копия программы / тарифа на каждого партнёра;
- хранение применяемой ставки только в UI без серверного расчёта;
- физическое удаление программы, по которой есть назначения или заявки;
- загрузка полного списка партнёров в карточку программы или в модалку назначения;
- изменение ставки уже оформленной заявки при правке программы.

## 1. Цель

Заменить раздел административного кабинета **«Условия финансирования»** на **«Лизинговые программы»**.

Нужно централизованно управлять:

- лизинговыми программами;
- базовыми условиями финансирования;
- индивидуальными условиями отдельных партнёров.

Партнёрский калькулятор и создание заявки должны брать **применяемую ставку**, а не «ставку, которую партнёр сам выбрал».

---

## 2. Ключевой принцип

Лизинговая программа создаётся **один раз**.

Программа назначается всем или выбранным партнёрам **ссылкой** (`program_id` + `partner_id`).

Для партнёра можно задать индивидуальные ставки по отдельным срокам. Это **исключения** из базовых условий, а не новая программа.

```
ЛИЗИНГОВАЯ ПРОГРАММА
        │
        ▼
  БАЗОВЫЕ УСЛОВИЯ (срок → ставка)
        │
        ├──────────────► Партнёр без исключений  → базовая ставка
        │
        └──────────────► Партнёр с исключением   → индивидуальная ставка
                                │
                                ▼
                         ПРИМЕНЯЕМАЯ СТАВКА
                                │
                    калькулятор / новая заявка
```

При создании программы партнёры **не назначаются**. Назначение — отдельный шаг в карточке программы.

## 3. Термины

| Термин | Смысл |
| --- | --- |
| Лизинговая программа | Набор условий оформления лизинга: имя, продукты, сроки, базовые ставки, статус |
| Базовые условия | Ставки в карточке программы. Пример: 24 мес. → 2,99% |
| Индивидуальные условия | Ставки конкретного партнёра, отличающиеся от базы. Пример: 24 мес. → 2,49% |
| Применяемая ставка | Ставка, которая реально идёт в калькулятор и заявку |
| Назначение | Связь программы с партнёром без копирования программы |
| Снимок условий | JSON/структура, сохранённая в заявке на момент оформления |

Примеры имён программ:

- `Лизинг_Базовый`
- `Лизинг_ТС_ЭЛЕКТРО/МЕБЕЛЬ_SALE`

## 4. Модель данных

Имена таблиц можно адаптировать под проект. Смысл и ограничения — обязательны.

### 4.1. `leasing_programs`

| Поле | Тип | Правила |
| --- | --- | --- |
| id | PK | |
| name | string | обязательно, уникально, trim |
| status | enum `active` \| `inactive` | при создании всегда `active` |
| created_at | datetime | |
| updated_at | datetime | |

Физического delete для использованных программ нет.

### 4.2. `program_products`

| Поле | Правила |
| --- | --- |
| program_id | FK |
| product_id | FK на существующий справочник продуктов |
| PK | `(program_id, product_id)` |

Продуктов у программы ≥ 1. Множественный выбор из справочника.

### 4.3. `program_terms`

| Поле | Правила |
| --- | --- |
| program_id | FK |
| term_months | целое > 0 |
| base_rate | число ≥ 0, хранить как decimal, не как строку с запятой |
| UNIQUE | `(program_id, term_months)` |

Один срок в программе — одна базовая ставка.

### 4.4. `program_assignments`

| Поле | Правила |
| --- | --- |
| program_id | FK |
| partner_id | FK |
| assigned_at | datetime |
| PK | `(program_id, partner_id)` |

Одна программа — много партнёров. Один партнёр — много программ. Повторное назначение того же партнёра идемпотентно, новую копию программы не создавать.

### 4.5. `individual_rates`

| Поле | Правила |
| --- | --- |
| program_id | FK |
| partner_id | FK |
| term_months | должен существовать в `program_terms` этой программы |
| rate | число ≥ 0 |
| PK | `(program_id, partner_id, term_months)` |

Запись существует только если ставка отличается от текущей логики исключения. Если индивидуальную ставку сбросили — строку удалить, не хранить «равную базе».

Индивидуальную ставку нельзя задать, если программа не назначена партнёру.

### 4.6. `applications` (заявки)

Обязательный снимок на момент оформления:

- program_id, program_name
- product_id, product_name
- term_months
- amount
- applied_rate
- rate_source = `base` \| `individual`
- base_rate, individual_rate на тот момент
- monthly_payment
- frozen_at

Последующие правки программы **не изменяют** эти поля.

### 4.7. `change_history`

Каждое изменение программ и условий:

| Поле | Обязательно |
| --- | --- |
| created_at | да |
| user_id, user_name, user_role | да |
| action | да, стабильный код |
| program_id, program_name | если относится к программе |
| term_months | если менялась ставка срока |
| old_value, new_value | если есть было/стало |
| apply_mode | если менялась базовая ставка |
| partner_id, partner_name | если изменение индивидуальное |
| details | свободный текст |

Коды `action`:

- `create_program`
- `rename_program`
- `change_products`
- `change_base_rate`
- `assign_all_partners`
- `assign_selected_partners`
- `set_individual_rate`
- `reset_individual_rate`
- `deactivate_program`
- `activate_program`
- `create_application`

## 5. Алгоритм применяемой ставки

Это единственный источник правды. И UI, и калькулятор, и заявка вызывают одну серверную функцию.

```
function resolveAppliedRate(programId, partnerId, termMonths):
  program = getProgram(programId)
  term = program.terms.find(termMonths)
  если term нет → ошибка unknown_term

  individual = find individual_rates(programId, partnerId, termMonths)
  если individual есть → { rate: individual.rate, source: "individual" }
  иначе → { rate: term.base_rate, source: "base" }
```

Примеры:

| База 24 мес. | Исключение партнёра А | Партнёр А | Партнёр Б без исключения |
| --- | --- | --- | --- |
| 2,99% | 2,49% | 2,49% / individual | 2,99% / base |
| 2,99% → 2,79% (без apply_to_all) | 2,49% остаётся | 2,49% | 2,79% |
| 2,99% → 2,79% + apply_to_all | исключение удалено | 2,79% / base | 2,79% |

Формат отображения: `2,99%` (запятая). В API и БД — число `2.99`.

## 6. Роли и права

Роли с полным доступом к управлению программами:

- Администратор
- Суперадминистратор

Права **одинаковые**. Не делать скрытых отличий.

Остальные роли, включая партнёра и менеджера:

- UI раздела «Лизинговые программы» не показывать;
- любой write/read API управления программами → `403`.

Партнёр:

- может читать свои назначенные программы;
- может считать калькулятор и создавать заявку;
- **не может** менять базовые или индивидуальные ставки.

Проверку роли делать на frontend и backend. Frontend — не защита, а навигация.

Ошибки API:

- нет авторизации → `401`
- нет роли → `403` с телом `{ "error": "Недостаточно прав", "code": "forbidden" }`

## 8. Экраны админки

### 8.1. Список программ

Таблица:

| Колонка | Источник |
| --- | --- |
| Программа | name |
| Продукты | чипы/список имён, не id |
| Партнёры | число назначений |
| Базовые | число назначенных партнёров без индивидуальных ставок |
| Индивидуальные | число назначенных партнёров, у которых есть хотя бы одно исключение |
| Статус | Активна / Неактивна |

Партнёров в этой таблице не выводить.

Кнопка **Создать программу**.

Клик по строке → карточка программы.

Счётчики:

```
partnersTotal = COUNT(assignments)
partnersIndividual = COUNT DISTINCT partner_id FROM individual_rates WHERE program_id
partnersBase = partnersTotal - partnersIndividual
```

### 8.2. Создание программы

Поля:

- Наименование — обязательно, уникально.
- Продукты — множественный выбор из справочника, ≥ 1.
- Сроки и ставки — таблица, кнопка **+ Добавить срок**.
  - срок в месяцах, целое > 0;
  - ставка ≥ 0;
  - один срок нельзя добавить дважды.

При успехе:

- статус `Активна`;
- назначенных партнёров 0;
- редирект в карточку;
- запись в историю `create_program`.

На форме создания **нет** выбора партнёров.

### 8.3. Карточка программы

Структура:

```
<Имя>
Статус: Активна | Неактивна

Продукты: ...

УСЛОВИЯ
Срок | Базовая ставка
[+ Добавить срок]

ПАРТНЁРЫ
Всего: N
Базовые условия: N
Индивидуальные условия: N
[Посмотреть партнёров]
[Назначить партнёрам]

ИСТОРИЯ ИЗМЕНЕНИЙ
последние записи + ссылка на полную историю

[Редактировать]
[Деактивировать] или [Активировать]
```

Полный список партнёров в карточке не показывать.

### 8.4. Назначение партнёрам

Модалка с двумя режимами.

**Всем партнёрам**

Текст подтверждения: «Программа будет назначена всем партнёрам».  
После подтверждения создать `program_assignments` на всех партнёров справочника.  
Существующие назначения не дублировать. Индивидуальные ставки не трогать.

**Выбранным партнёрам**

- поле поиска по названию;
- запрос не слать, пока меньше 2 символов;
- не загружать полный справочник;
- множественный выбор;
- пагинация / подгрузка страницами по 8–10;
- кнопка **Назначить**.

После назначения партнёры используют базовые условия, пока нет исключений.

### 8.5. Список партнёров программы

Открывается по **Посмотреть партнёров**.

Шапка: Всего / Базовые / Индивидуальные.

Фильтры: Все | Базовые условия | Индивидуальные условия.  
Поиск по названию.  
Пагинация обязательна, размер страницы 10.

Таблица:

| Партнёр | Тип условий | Индивидуальных изменений | Действие |
| --- | --- | --- | --- |
| Партнёр А | Базовые | 0 | Открыть |
| Партнёр Б | Индивидуальные | 1 | Открыть |

«Индивидуальных изменений» = число сроков с исключением у этого партнёра в этой программе.

Открыть → карточка партнёра, якорь на блок программ.

### 8.6. Карточка партнёра, блок программ

Для каждой назначенной программы:

```
Лизинг_Базовый
Активна | Неактивна

Срок | Базовая ставка | Ставка партнёра
12   | 1,99%         | 1,99%
24   | 2,99%         | 2,49%   ← бейдж «Индивидуальная»

[Настроить индивидуальные условия]
```

Ставка партнёра визуально отличается от базы, если `source = individual` (цвет + бейдж). Не выделять строку, если значения совпали после сброса.

### 8.7. Индивидуальные условия

Форма: все сроки программы, поле ставки, пустое значение = «использовать базу».

Сохранить → upsert исключений, пустые → delete.

**Сбросить индивидуальное условие** по сроку:

1. подтверждение;
2. удаление строки исключения;
3. применяемая ставка снова базовая.

Партнёр этот экран не видит.

### 8.8. Изменение базовой ставки

Если программа уже назначена хотя бы одному партнёру и изменилась ставка существующего срока, **не сохранять сразу**.

Показать:

```
Вы изменили базовую ставку:
24 месяца: 2,99% → 2,79%

По программе:
• N партнёров используют базовые условия;
• M партнёров имеют индивидуальные условия по этому сроку.
```

Три варианта:

| Код | Подпись | Поведение |
| --- | --- | --- |
| `apply_to_base` | Применить к партнёрам с базовыми условиями | Обновить `program_terms`. Исключения не трогать. Это действие по умолчанию |
| `apply_to_all` | Применить ко всем партнёрам | Обновить `program_terms` и **удалить** `individual_rates` по этому сроку. Требует второе подтверждение |
| `change_program_only` | Изменить только базовую программу | Обновить `program_terms`. Исключения не трогать |

Для `apply_to_all` показать:

```
Внимание
У M партнёров установлены индивидуальные условия.
При применении ко всем партнёрам индивидуальные ставки для данного срока
будут заменены новой базовой ставкой.
```

Без `confirmApplyToAll = true` сервер возвращает `409 confirm_apply_to_all`.

В текущей модели `apply_to_base` и `change_program_only` дают одинаковый эффект на данные (меняется только база). Оба пункта в UI обязательны, в историю писать выбранный `apply_mode`.

Если сроков изменили несколько — показать каждый и применить выбранный режим ко всем изменённым срокам.

### 8.9. Изменение продуктов

Если программа уже назначена, перед сохранением показать последствия: сколько партнёров затронуто, какие продукты были и какие будут.  
Копии программ не создавать. Меняется сама программа.

Сервер: без `confirmProductChange` → `409 confirm_product_change`.

### 8.10. Деактивация и активация

Деактивация:

- подтверждение;
- статус `inactive`;
- программа не доступна для новых заявок и калькулятора;
- исторические заявки не меняются.

Активация:

- статус `active`;
- снова доступна назначенным партнёрам.

Кнопки удаления нет.

### 8.11. История

В карточке — последние записи. Полный список — отдельный экран с пагинацией и фильтром по программе.

Отображение записи:

```
07.09.2026 14:35
Иванов И.И.
Администратор

Программа: Лизинг_Базовый
Срок: 24 месяца
2,99% → 2,79%
Применение: партнёры с базовыми условиями
```

## 9. Кабинет партнёра

Партнёр не выбирает и не вводит ставку.

Калькулятор:

- программа — только назначенные ему;
- продукт — только продукты этой программы;
- срок — только сроки программы;
- сумма предмета лизинга.

Ответ калькулятора обязательно содержит:

- `baseRate`
- `individualRate` (или null)
- `appliedRate`
- `rateSource`
- `monthlyPayment`

В заявку писать `appliedRate` и полный снимок. Заголовок/бейдж «Индивидуальная», если `rateSource = individual`.

Неактивная программа в расчёте новой заявки → ошибка `inactive_program`.

Формула платежа должна быть той же, что уже принята в продукте (аннуитет или удорожание). Не менять бизнес-формулу «заодно» с этим ТЗ. Если формулы в коде нет, зафиксировать текущую и переиспользовать.

## 10. API

Адаптировать префиксы под проект. Контракты сохранить.

Все write-методы программ — только admin/superadmin.  
Идемпотентность: повторный assign того же партнёра не создаёт вторую связь и не плодит программу.

### 10.1. Программы

`GET /programs`  
Список с продуктами, сроками и агрегатами партнёров.

`POST /programs`  
Тело:

```json
{
  "name": "Лизинг_Экспресс",
  "productIds": [1, 2],
  "terms": [
    { "termMonths": 12, "baseRate": 1.99 },
    { "termMonths": 24, "baseRate": 2.49 }
  ]
}
```

Ошибки: `required_name`, `duplicate_name`, `invalid_products`, `invalid_terms`, `duplicate_term`, `invalid_rate`.

`GET /programs/:id`

`PATCH /programs/:id`  
Тело может содержать `name`, `productIds`, `terms`, `applyMode`, `confirmApplyToAll`, `confirmProductChange`.

Если меняются базовые ставки и есть назначения, без `applyMode` → `409 apply_mode_required` плюс preview:

```json
{
  "code": "apply_mode_required",
  "changes": [
    {
      "termMonths": 24,
      "oldRate": 2.99,
      "newRate": 2.79,
      "partnersBase": 120,
      "partnersIndividual": 8
    }
  ],
  "counts": { "partnersTotal": 128, "partnersBase": 120, "partnersIndividual": 8 }
}
```

## 11. Бизнес-правила

| ID | Правило |
| --- | --- |
| BR-01 | Одна программа может быть назначена нескольким партнёрам |
| BR-02 | Один партнёр может иметь несколько программ |
| BR-03 | В одной программе один срок — одна базовая ставка |

| BR-14 | Все изменения программ и условий пишутся в историю |

## 12. Миграция со старых «Условий финансирования»

Порядок:

1. Развернуть новые таблицы рядом со старыми.
2. Перенести каждую уникальную программу/набор условий в `leasing_programs`.
3. Сохранить связи с продуктами.
4. Сохранить связи с партнёрами как `program_assignments`, **не** как копии программ.
5. Если у партнёра ставка по сроку отличалась от базы программы — записать `individual_rates`.
6. Если в старой модели у каждого партнёра была полная копия тарифа:
   - сгруппировать идентичные наборы срок→ставка в одну программу, если это один и тот же продуктовый оффер;
   - иначе: одна логическая программа + исключения там, где ставки разошлись.
7. Переключить калькулятор и создание заявки на `resolveAppliedRate`.
8. Старые заявки: либо оставить как есть, либо один раз заполнить снимок из тогдашних значений. Не пересчитывать прошлые заявки новыми ставками.
9. Заменить пункт меню.
10. После проверки отключить запись в старые сущности. Старый UI убрать.

Миграцию делать идемпотентной. Логировать, сколько программ / назначений / исключений перенесено.

## 13. Нефункциональные требования

- Поиск партнёров: debounce ~250 мс, лимит страницы ≤ 50.
- Список партнёров программы всегда с `LIMIT/OFFSET`.
- Агрегаты в списке программ считать запросами COUNT, не загрузкой всех связей в память.
- Изменение программы, назначений и исключений — в транзакции вместе с историей.
- Ставки считать decimal, без накопительной ошибки float в сравнениях. Если в языке нет decimal — сравнивать через округление до 2 знаков.
- Тексты UI на русском, как в этом ТЗ.

## 15. Приёмка

Обязательные проверки. Каждая — автоматизированный тест и/или ручной сценарий.

1. Создана программа со статусом «Активна», партнёров 0.
2. Имя дубликата не сохраняется.
3. Дубль срока в одной программе не сохраняется.
4. Назначение всем не создаёт N копий программы: `COUNT(programs where name=X) = 1`.
5. Назначение выбранным работает через поиск, полный список не грузится.
6. Партнёр А с исключением 24 мес. 2,49% получает 2,49% в карточке, калькуляторе и заявке.
7. Партнёр Б без исключения получает 2,99%.
8. Смена базы 2,99% → 2,79% в режиме по умолчанию: А остаётся 2,49%, Б становится 2,79%.
9. Режим «только программа»: то же для ставок.
10. Режим «ко всем» без второго подтверждения не проходит.
11. Режим «ко всем» с подтверждением: исключение А по 24 мес. исчезает, оба получают 2,79%.
12. Сброс исключения возвращает базу.
13. Партнёрский API смены ставки → 403.
14. Менеджер/прочая роль → 403 на `/programs`.
15. Админ и суперадмин проходят одни и те же write-методы.
16. Неактивная программа не считается в калькуляторе и не создаёт заявку.
17. После правки программы `applications.applied_rate` и снимок старой заявки не меняются.
18. В истории есть дата, ФИО, роль, действие, программа, срок, было/стало, apply_mode, партнёр для индивидуальных.
19. Смена продуктов назначенной программы требует подтверждения.
20. Пункт меню «Условия финансирования» отсутствует, есть «Лизинговые программы».

## 17. Критерии готовности

Функция готова, когда:

- старый раздел заменён;
- данные перенесены без потери индивидуальных ставок;
- калькулятор и заявка используют серверную применяемую ставку;
- админ может назначить программу всем/выбранным без копий;
- опасное «применить ко всем» требует второго подтверждения;
- автотесты из раздела 16 зелёные;
- роли проверены на API, не только кнопками.

Если Codex находит в проекте уже существующие сущности тарифов/условий — мапить на эту модель, а не плодить параллельный справочник с теми же смыслами.
