# Техническое задание: логика лизинговых программ

Документ описывает **правила работы** функционала. Это источник истины для разработки. Стек, фреймворк и текущий код кабинета в расчёт не брать: реализовать нужно именно эту логику.

Если в существующей системе «условия финансирования» хранятся как копия тарифа на каждого партнёра — эту модель заменить. Новая логика копий не создаёт.

---

## 1. Задача

В административном кабинете раздел **«Условия финансирования»** заменить разделом **«Лизинговые программы»**.

Система должна уметь:

- завести одну лизинговую программу с базовыми ставками;
- назначить её всем или части партнёров, не копируя программу;
- для отдельных партнёров задать исключения по срокам;
- в калькуляторе и новой заявке всегда брать **применяемую** ставку;
- при смене базы решать, трогать ли исключения;
- хранить в уже оформленной заявке условия на момент оформления.

---

## 2. Принцип, который нельзя нарушать

Программа существует в одном экземпляре.

Партнёр **не получает свою копию** программы, тарифа, таблицы сроков или набора ставок.

У партнёра есть только:

1. факт назначения: «партнёру X доступна программа Y»;
2. необязательные исключения: «у партнёра X по программе Y на срок T ставка другая».

Применяемая ставка **не хранится** отдельным полем «текущая ставка партнёра», которое живут своей жизнью. Она **вычисляется** в момент чтения:

- есть исключение по этому сроку → ставка исключения;
- нет исключения → базовая ставка программы на этот срок.

Поэтому если админ меняет базовую ставку 24 мес. с 2,99% на 2,79% и **не** сбрасывает исключения, то:

- все назначенные партнёры без исключения на 24 мес. сразу видят 2,79% — им ничего отдельно «рассылать» не нужно;
- партнёры с исключением на 24 мес. по-прежнему видят свою ставку.

Именно поэтому запрещено:

- клонировать программу при назначении;
- дублировать таблицу сроков в карточке партнёра как основной источник;
- записывать партнёру все сроки «как его ставки», даже если они равны базе.

## 3. Словарь

Слова ниже использовать буквально. Если реализация называет сущности иначе, смысл должен совпасть.

**Лизинговая программа** — именованный набор условий: наименование, список продуктов, список сроков с базовыми ставками, статус. Примеры имён: `Лизинг_Базовый`, `Лизинг_ТС_ЭЛЕКТРО/МЕБЕЛЬ_SALE`.

**Продукт программы** — вид предмета лизинга из справочника продуктов (например «Транспортные средства», «Электроника», «Мебель»). У программы может быть несколько продуктов. Ставки **не** зависят от продукта: все продукты программы живут на одной сетке сроков и ставок.

**Срок** — длительность в месяцах. Целое число больше нуля. Примеры: 12, 18, 24, 36, 48. В одной программе один и тот же срок не может встречаться дважды.

**Базовая ставка** — ставка, записанная в программе на конкретный срок. Одна на пару «программа + срок».

**Назначение** — связь «программа доступна партнёру». Без назначения партнёр программу не видит в калькуляторе и ему нельзя задать исключение.

**Исключение / индивидуальная ставка** — явно сохранённое значение ставки для тройки «программа + партнёр + срок». Пока записи нет, индивидуальной ставки нет.

**Партнёр с базовыми условиями по программе** — партнёр назначен на программу и **не имеет ни одного исключения** по этой программе (ни на одном сроке).

**Партнёр с индивидуальными условиями по программе** — партнёр назначен на программу и имеет хотя бы одно исключение по любому сроку этой программы.

**Партнёр с исключением по сроку T** — у партнёра есть запись исключения именно на срок T этой программы. Это более узкое понятие, чем предыдущее: у партнёра может быть исключение на 36 мес. и не быть на 24 мес.

**Применяемая ставка** — ставка, которую система обязана подставить в калькулятор и в новую заявку для данной программы, партнёра и срока.

**Снимок условий заявки** — значения, записанные в заявку в момент оформления. Они больше не пересчитываются.

**Активная программа** — доступна для калькулятора и новых заявок у назначенных партнёров.

**Неактивная программа** — для новых расчётов и заявок недоступна. Назначения и исключения не удаляются. Старые заявки не меняются.

## 4. Что хранится, а что вычисляется

### 4.1. Хранить обязательно

- программу: имя, статус, даты;
- состав продуктов программы;
- базовые сроки и базовые ставки;
- назначения программа ↔ партнёр;
- исключения программа ↔ партнёр ↔ срок ↔ ставка;
- в заявке — снимок условий;
- журнал изменений.

### 4.2. Не хранить как самостоятельную сущность

- «ставку партнёра по сроку», если это просто копия базы;
- копию программы на партнёра;
- отдельный статус «партнёр использует базу / индивидуально» — это выводится из наличия исключений;
- применяемую ставку отдельно от исключения и базы, кроме снимка в заявке.

### 4.3. Как считать цифры на экранах

Пусть `A` — число назначений программы.  
Пусть `I_prog` — число **различных** назначенных партнёров, у которых по этой программе есть хотя бы одно исключение.  
Пусть `I_term(T)` — число **различных** назначенных партнёров, у которых есть исключение именно на срок T.

Тогда:

| Показатель | Формула |
| --- | --- |
| Всего партнёров программы | `A` |
| Партнёры с индивидуальными условиями (по программе) | `I_prog` |
| Партнёры с базовыми условиями (по программе) | `A − I_prog` |
| Партнёры с исключением на срок T | `I_term(T)` |
| Партнёры без исключения на срок T | `A − I_term(T)` |
| Число индивидуальных изменений у партнёра в программе | число сроков, по которым у него есть исключение |

Важно: `A − I_prog` и `A − I_term(T)` — разные числа.

Пример. Программа назначена 128 партнёрам. У 8 есть исключение на 24 мес. У 2 из этих 8 также есть исключение на 36 мес. Больше исключений нет.

- В списке программ: Партнёры 128, Базовые 120, Индивидуальные 8.
- При смене ставки **только 24 мес.**: затронуты исключением 8, базу 24 мес. получат 120.
- При смене ставки **только 36 мес.**: затронуты исключением 2, базу 36 мес. получат 126.
- У партнёра с двумя исключениями в таблице партнёров программы «Индивидуальных изменений» = 2.

Диалог смены базовой ставки по сроку T обязан показывать `A − I_term(T)` и `I_term(T)`, а не путать их с программными 120/8, если меняется другой срок.

## 5. Алгоритм применяемой ставки

Единственная точка расчёта для карточки партнёра, калькулятора и новой заявки.

Вход: `program`, `partner`, `termMonths`.

Шаги:

1. Программа должна существовать. Иначе ошибка «программа не найдена».
2. Партнёр должен существовать. Иначе ошибка «партнёр не найден».
3. Должно существовать назначение этой программы этому партнёру. Иначе ошибка «программа не назначена партнёру». Для **новой** заявки и калькулятора этого достаточно, чтобы отказать. Для админского просмотра неназначенную программу просто не показывать в блоке партнёра.
4. В программе должен быть срок `termMonths`. Иначе ошибка «срок отсутствует в программе».
5. Найти исключение по ключу (программа, партнёр, срок).
6. Если исключение найдено — применяемая ставка = ставка исключения, источник `individual`.
7. Если исключения нет — применяемая ставка = базовая ставка этого срока, источник `base`.

Никаких других слоёв приоритета нет: нет региона, нет объёма сделки, нет ручного ввода партнёром, нет «лучшей из нескольких программ». Если у партнёра несколько программ, применяемая ставка считается **внутри выбранной программы**.

Псевдокод:

```
если нет назначения (program, partner) → отказ
срок = базовые сроки программы, где months = termMonths
если срок не найден → отказ
исключение = найти (program, partner, termMonths)
если исключение есть → { rate: исключение.rate, source: individual }
иначе → { rate: срок.baseRate, source: base }
```

### 5.1. Примеры

База программы:

| Срок | База |
| ---: | ---: |
| 12 | 1,99% |
| 18 | 2,49% |
| 24 | 2,99% |
| 36 | 2,99% |
| 48 | 2,99% |

Партнёр А: исключение 24 мес. = 2,49%.  
Партнёр Б: исключений нет.

| Запрос | Результат |
| --- | --- |
| А, 12 мес. | 1,99% / base |
| А, 24 мес. | 2,49% / individual |
| Б, 24 мес. | 2,99% / base |
| А, 60 мес. | ошибка: срока нет |
| Партнёр В, которому программа не назначена, любой срок | ошибка: не назначена |

После смены базы 24 мес. на 2,79% **без** сброса исключений:

| Запрос | Результат |
| --- | --- |
| А, 24 мес. | 2,49% / individual |
| Б, 24 мес. | 2,79% / base |
| А, 12 мес. | 1,99% / base |

После той же смены со сбросом исключений по сроку 24:

| Запрос | Результат |
| --- | --- |
| А, 24 мес. | 2,79% / base |
| Б, 24 мес. | 2,79% / base |
| А, если было ещё исключение на 36 мес. | 36 мес. по-прежнему individual |

### 5.2. Равенство чисел не отменяет исключение

Если у партнёра сохранено исключение 2,49%, а базу потом тоже поставили 2,49%, источник всё равно `individual`, пока запись исключения не удалена. Бейдж «Индивидуальная» остаётся. Партнёр не «прилипает» к будущим изменениям базы, пока исключение живо.

Если админ явно сохраняет партнёру значение, совпадающее с текущей базой, это тоже исключение: ставка зафиксирована и больше не следит за базой.

Сброс исключения — единственный способ вернуть слежение за базой.

## 6. Жизненный цикл программы

### 6.1. Создание

Вход: наименование, набор продуктов, набор пар (срок, базовая ставка).

Партнёры на этом шаге **не выбираются и не назначаются**.

Проверки до записи:

1. Наименование после обрезки пробелов непустое.
2. Наименование уникально среди всех программ, без учёта статуса. Нельзя создать вторую `Лизинг_Базовый`, даже если первая неактивна.
3. Выбран хотя бы один продукт, все id из справочника продуктов.
4. Есть хотя бы один срок.
5. Каждый срок — целое число месяцев > 0.
6. Каждая ставка — число ≥ 0, точность до 2 знаков (1,99 а не 1,999).
7. Сроки внутри программы уникальны.

Результат:

- программа создана;
- статус **Активна**;
- число назначений = 0;
- исключений нет;
- в журнал: кто создал, роль, имя программы.

После создания программа ещё никому не доступна в калькуляторе.

### 6.2. Редактирование имени

Новое имя: те же проверки уникальности, исключая саму программу.  
Назначения и исключения не затрагиваются.  
В заявках уже записанное `program_name` снимка не переписывать.

### 6.3. Статусы

Два статуса: `Активна` и `Неактивна`. Других нет.

Переходы:

- Активна → Неактивна: действие «Деактивировать», нужно подтверждение.
- Неактивна → Активна: действие «Активировать».
- Повторная установка того же статуса — пустая операция, без новой записи в журнал.

Деактивация **не** делает:

- не снимает назначения;
- не удаляет исключения;
- не меняет старые заявки;
- не запрещает админу смотреть карточку и исключения.

Деактивация **делает**:

- программа не участвует в калькуляторе новой сделки;
- нельзя создать новую заявку по этой программе.

Физическое удаление запрещено, если есть хотя бы одно назначение или хотя бы одна заявка со ссылкой на программу. В интерфейсе кнопки удаления нет. Неиспользованную программу (нет назначений и заявок) удалять тоже не обязательно: достаточно деактивации. Для этой версии удаление не реализовывать.

### 6.4. Продукты программы

Продукты — множественный набор из справочника. Ставки от продукта не зависят.

Смена продуктов не создаёт новые программы и не переназначает партнёров. Назначенные партнёры начинают видеть новый состав продуктов.

Если программа уже кому-то назначена, сохранить новый состав можно только после подтверждения. Текст подтверждения обязан сказать:

- сколько партнёров уже назначено;
- какой состав продуктов был;
- какой станет.

Зачем подтверждение: партнёрский калькулятор начнёт предлагать другие продукты на тех же ставках.

Пустой набор продуктов сохранить нельзя.

## 7. Сроки и базовые ставки

### 7.1. Добавление срока

Админ добавляет строку: срок + базовая ставка.  
Срок не должен совпадать с уже существующим в этой программе.

Эффект сразу после сохранения:

- все **уже назначенные** партнёры получают этот срок с базовой ставкой автоматически;
- исключений на новый срок нет, пока их явно не зададут;
- отдельно «разослать срок партнёрам» не нужно.

### 7.2. Изменение базовой ставки существующего срока

Это самое чувствительное действие. Разбор — раздел 9.

### 7.3. Удаление срока из программы

Если срок убирают из программы:

- базовая строка срока удаляется;
- все исключения по этому сроку этой программы удаляются;
- калькулятор больше не предлагает этот срок;
- старые заявки с этим сроком не меняются.

Перед удалением срока, если есть назначения, показать, что исключения по сроку будут сняты. Если исключений по сроку нет, достаточно обычного сохранения сетки сроков.

### 7.4. Нельзя

- дважды завести 24 мес. в одной программе;
- оставить программу без единого срока;
- хранить ставку строкой «2,99%» как основной тип: в данных это число 2.99, в UI — `2,99%`.

---

## 8. Назначение программы партнёрам

Назначение — отдельная операция после создания. Не смешивать с формой создания.

### 8.1. Общие правила

- Назначение создаёт только связь программа–партнёр.
- Таблица базовых сроков не копируется.
- Исключения сами не появляются.
- Повторное назначение уже назначенного партнёра ничего не ломает: связь одна.
- «Всем партнёрам» = все партнёры, которые есть в справочнике **на момент операции**. Партнёры, заведённые позже, программу **автоматически не получают**.
- Назначать можно активную и неактивную программу. Неактивная всё равно не пойдёт в новый калькулятор, пока её не активируют.
- Один партнёр может иметь несколько программ. Пересечения продуктов между программами допустимы. Какую программу использовать, выбирает пользователь калькулятора, система «лучшую ставку» сама не выбирает.

Отзыв назначения (снять программу с партнёра) в этой версии **не требуется**. Не реализовывать, пока не появится отдельное требование.

### 8.2. Режим «Всем партнёрам»

Предусловие: открыта карточка программы.

Шаги:

1. Админ нажимает «Назначить партнёрам».
2. Выбирает «Всем партнёрам».
3. Система показывает: «Программа будет назначена всем партнёрам.»
4. После подтверждения для каждого партнёра справочника создаётся связь, если её ещё не было.
5. В журнал: действие назначения всем, число партнёров, программа, кто сделал.

Исключения уже назначенных партнёров не сбрасывать.

### 8.3. Режим «Выбранным партнёрам»

Шаги:

1. Админ выбирает «Выбранным партнёрам».
2. Вводит название (поиск). Пока меньше 2 символов — список не грузить.
3. Система возвращает страницу совпадений, не весь справочник.
4. Админ отмечает одного или нескольких.
5. Нажимает «Назначить».
6. Связи создаются только для отмеченных.

Нельзя:

- отдать на фронт полный массив всех партнёров «на всякий случай»;
- назначить партнёра, которого нет в справочнике.

Если никого не выбрали — ошибка, назначение не выполнять.

### 8.4. Что видит партнёр после назначения

В калькуляторе появляются активные назначенные программы.  
По каждому сроку ставка сначала равна базе, пока нет исключений.

## 9. Изменение базовой ставки: три режима

Ситуация: в программе на срок T база меняется с `old` на `new`, `old ≠ new`. Программа уже назначена хотя бы одному партнёру.

Сохранять сразу нельзя. Сначала показать влияние, затем выбрать режим.

### 9.1. Что показать до сохранения

Для каждого изменённого срока T отдельно:

```
Срок T: old% → new%
Партнёров без исключения на этот срок: A − I_term(T)
Партнёров с исключением на этот срок: I_term(T)
```

Если изменили несколько сроков — перечислить все.

Три варианта:

1. Применить к партнёрам с базовыми условиями
2. Применить ко всем партнёрам
3. Изменить только базовую программу

### 9.2. Режим 1 — к партнёрам с базовыми условиями

Режим по умолчанию.

Действие с данными:

- обновить базовую ставку срока T на `new`;
- исключения по сроку T **не удалять и не переписывать**.

Эффект:

- у кого не было исключения на T, применяемая ставка становится `new` автоматически;
- у кого было исключение на T, применяемая ставка не меняется.

Это следует из модели «ставка не копируется». Отдельно обходить партнёров и писать им `new` запрещено.

Пример. База 24 мес. 2,99% → 2,79%. У А исключение 2,49%. У Б исключений нет.

- база = 2,79%
- А = 2,49%
- Б = 2,79%

### 9.3. Режим 2 — ко всем партнёрам

Опасное действие. Нужны два шага подтверждения:

1. выбор этого режима в списке из трёх;
2. отдельное предупреждение и явное согласие.

Текст предупреждения, подставить реальное M = `I_term(T)`:

```
Внимание
У M партнёров установлены индивидуальные условия.
При применении изменения ко всем партнёрам индивидуальные ставки
для данного срока будут заменены новой базовой ставкой.
```

Если M = 0, второе предупреждение всё равно можно показать коротко, но блокировать режим не нужно.

Действие с данными:

- обновить базовую ставку срока T на `new`;
- **удалить** все исключения этой программы по сроку T.

Исключения по другим срокам не трогать.

Эффект: у всех назначенных партнёров применяемая ставка на T становится `new`, источник `base`.

Без второго подтверждения сохранение отклонить.

### 9.4. Режим 3 — только базовая программа

Действие с данными то же, что в режиме 1: меняется только база, исключения живут.

Зачем два пункта с одинаковым эффектом на данные: в старых системах с копиями тарифа «обновить шаблон» и «обновить всех без персональных ставок» были разными операциями. В правильной модели они совпадают. Оба пункта в UI оставить. В журнале записать, какой пункт человек нажал. Не делать третий скрытый путь, который снова копирует ставки партнёрам.

### 9.5. Если программа никому не назначена

Диалог трёх режимов не нужен. Достаточно сохранить новую базу. В журнале `apply_mode` можно не писать либо писать `change_program_only`.

### 9.6. Если меняют сразу несколько сроков

Выбранный режим применяется к каждому изменённому сроку одинаково. Нельзя в одном сохранении для 24 мес. выбрать «ко всем», а для 36 мес. «только база». Если продукту это понадобится — отдельное требование, сейчас нет.

### 9.7. Запрещено при смене базы

- молча затирать исключения;
- записывать всем партнёрам новую ставку в их «личные» поля;
- менять снимки уже оформленных заявок;
- менять исключения по срокам, которые в этом сохранении не менялись, кроме случая удаления срока (раздел 7.3).

## 10. Индивидуальные условия

### 10.1. Когда можно задать

Только если программа назначена партнёру.  
Только по сроку, который есть в программе.  
Только роли администратора и суперадминистратора.

Партнёр не создаёт, не правит и не сбрасывает исключения никаким способом, включая прямой вызов API.

### 10.2. Установка

Админ в карточке партнёра открывает назначенную программу → «Настроить индивидуальные условия».

Система показывает базовые сроки и текущие применяемые значения.  
Админ вводит новые значения для одного или нескольких сроков и сохраняет.

Для каждого срока в форме:

- пусто / «очистить» → исключения быть не должно (если было — это сброс этого срока);
- число ≥ 0 → создать или обновить исключение на это значение.

После сохранения:

- применяемая ставка по изменённым срокам берётся из исключения;
- в UI рядом со значением — признак «Индивидуальная»;
- рядом показывается база, чтобы было видно расхождение.

Пример:

Было: 24 мес. база 2,99%, исключений нет, применяемая 2,99%.  
Поставили 2,49%.  
Стало: база 2,99%, индивидуальная 2,49%, применяемая 2,49%.

### 10.3. Сброс

Отдельное действие «Сбросить индивидуальное условие» по конкретному сроку.

1. Подтверждение.
2. Удаление записи исключения по этому сроку.
3. Применяемая ставка снова равна текущей базе (не старой базе на момент создания исключения).

Пример. База уже успела стать 2,79%, исключение было 2,49%. После сброса применяемая = 2,79%, не 2,99%.

Сброс без подтверждения не выполнять.

Сброс всех сроков сразу в этой версии не обязателен: достаточно посрокового.

### 10.4. Ограничения

- на тройку программа–партнёр–срок максимум одна индивидуальная ставка;
- нельзя завести исключение на срок, которого нет в программе;
- нельзя завести исключение без назначения;
- если срок из программы удалили, связанные исключения исчезают вместе с ним.

## 11. Калькулятор и заявка

### 11.1. Калькулятор

Актор: партнёр (система считает ставку сама).

Доступные программы: назначенные этому партнёру **и** в статусе «Активна».  
Доступные продукты: продукты выбранной программы.  
Доступные сроки: сроки выбранной программы.

Партнёр вводит сумму предмета лизинга. Ставку не вводит и не корректирует.

Система:

1. проверяет назначение, статус активна, продукт входит в программу, срок есть, сумма > 0;
2. считает применяемую ставку алгоритмом из раздела 5;
3. считает платёж **той формулой, которая уже принята в продукте** (этот документ формулу лизингового платежа не меняет);
4. в расчёт платежа подставляется именно применяемая ставка, не база «на всякий случай».

Ответ калькулятора обязан содержать и базу, и исключение, и применяемую, и источник. Чтобы в UI можно было подписать «индивидуальное условие».

Неактивная программа: либо не показывать в списке, либо показывать недоступной. Новая заявка по ней невозможна.

### 11.2. Создание заявки

Создаётся только из серверного пересчёта, не из ставки, пришедшей с клиента. Если клиент прислал `appliedRate`, это поле игнорировать.

В заявку записать снимок минимум:

- id и имя программы на тот момент;
- id и имя продукта;
- срок;
- сумма;
- базовая ставка на тот момент;
- индивидуальная ставка на тот момент или признак, что её не было;
- применяемая ставка;
- источник `base` | `individual`;
- платёж;
- дата-время фиксации.

Дальше:

- смена базы не меняет заявку;
- сброс исключения не меняет заявку;
- деактивация программы не меняет заявку;
- переименование программы не обязано менять имя в старом снимке.

### 11.3. Несколько программ у одного партнёра

Партнёр сам выбирает программу в калькуляторе.  
Система не смешивает сетки ставок двух программ.  
Не выбирает автоматически более низкую ставку.

## 12. Роли

### 12.1. Администратор и суперадминистратор

Права **совпадают полностью**. Не вводить скрытых ограничений для администратора.

Могут:

- создавать и править программы;
- менять продукты и сроки;
- активировать и деактивировать;
- назначать всем и выбранным;
- задавать и сбрасывать индивидуальные ставки;
- выбирать любой из трёх режимов смены базы;
- видеть списки, карточки, историю, заявки.

### 12.2. Партнёр

Может: калькулятор по своим активным назначенным программам, создание заявки, просмотр своих заявок.

Не может: менять базу, исключения, состав программ, назначения, статусы.

Скрытие кнопок в UI недостаточно. Сервер должен отказать.

### 12.3. Все остальные роли

Нет доступа к управлению программами.  
Сервер на операции управления отвечает отказом в доступе.

Проверку роли делать и на экранах, и на сервере.

## 13. Журнал изменений

Писать после каждого успешного изменения программ, назначений, исключений и (по возможности) создания заявки.

В записи всегда:

- дата и время;
- ФИО пользователя;
- роль;
- код действия;
- программа;
- срок, если действие про ставку;
- старое и новое значение, если есть;
- режим применения, если меняли базу;
- партнёр, если действие индивидуальное или касается одного партнёра;
- пояснение.

Примеры формулировок:

```
07.09.2026 14:35
Иванов И.И.
Администратор
Программа: Лизинг_Базовый
Срок: 24 месяца
2,99% → 2,79%
Применение: партнёры с базовыми условиями
```

```
Назначение выбранным партнёрам
Программа: Лизинг_Базовый
Назначено: 3
Копия программы не создавалась
```

```
Индивидуальная ставка
Партнёр: ИП Козлов А.В.
Программа: Лизинг_Базовый
Срок: 24 месяца
база 2,99% → исключение 2,49%
```

Журнал не редактируется пользователем. Не удаляется вместе с деактивацией программы.

## 14. Экраны: какая логика должна быть видна

Ниже не макет, а обязательное поведение.

### 14.1. Список программ

Колонки: имя, продукты, число партнёров, число базовых, число индивидуальных, статус.  
Партнёров списком не выводить.  
Создание — кнопка «Создать программу».  
Строка открывает карточку.

### 14.2. Создание

Только имя, продукты, сроки/ставки.  
Нет виджета партнёров.  
После успеха статус «Активна», назначений 0.

### 14.3. Карточка программы

Блок условий: таблица срок / базовая ставка, добавление срока.  
Блок партнёров: три числа и кнопки «Посмотреть партнёров», «Назначить партнёрам».  
Блок истории: последние события.  
Действия: редактировать, деактивировать либо активировать.

### 14.4. Список партнёров программы

Фильтры: все / базовые / индивидуальные — в смысле **программы** (есть ли хотя бы одно исключение).  
Поиск по названию.  
Страницы обязательны.  
Колонка «Индивидуальных изменений» — число сроков-исключений.  
«Открыть» ведёт в карточку партнёра.

### 14.5. Карточка партнёра

Для каждой назначенной программы таблица:

Срок | База | Ставка партнёра

Если источник individual — ставка партнёра визуально другая и подписана «Индивидуальная».  
Кнопка настройки исключений только у админа/суперадмина.

### 14.6. Кабинет партнёра

Нет полей редактирования ставки.  
После расчёта видно применяемую ставку и, если надо, пометку «индивидуальная».  
Создание заявки фиксирует снимок.

## 15. Замена старого раздела «Условия финансирования»

Цель миграции — получить ровно эту модель, а не перенести старые копии как есть.

Правила переноса:

1. Каждый логически единый оффер (одно имя/продуктовый набор/сетка базы) становится **одной** программой.
2. Связь партнёра с оффером становится назначением, не новой программой.
3. Если ставка партнёра по сроку совпадала с базой оффера — исключение **не** создавать.
4. Если ставка партнёра по сроку отличалась — создать исключение с этим значением.
5. Если в старой системе у партнёра была полная копия и её потом меняли независимо, а «шаблона» уже нет: восстановить программу как общий шаблон по самой частой сетке, отличия разложить в исключения. Не оставлять 1000 программ-клонов.
6. Исторические заявки не пересчитывать новой логикой. Либо оставить как хранились, либо один раз заполнить снимок из тогдашних цифр.
7. Калькулятор новых расчётов переключить на алгоритм раздела 5.
8. Пункт меню «Условия финансирования» убрать, вместо него «Лизинговые программы».

После миграции инвариант: количество программ не растёт пропорционально числу партнёров.

## 16. Полные сценарии

### Сценарий A. Новая программа и выборочное назначение

1. Админ создаёт `Лизинг_Базовый`, продукты «ТС», сроки 12…48 и базовые ставки. Партнёров 0.
2. Назначает трём партнёрам через поиск.
3. У всех троих в калькуляторе 24 мес. = 2,99%.
4. Карточка программы: Всего 3, Базовые 3, Индивидуальные 0.

### Сценарий B. Исключение одному партнёру

1. В карточке партнёра А на 24 мес. ставят 2,49% и сохраняют.
2. Карточка программы: Всего 3, Базовые 2, Индивидуальные 1.
3. Калькулятор А, 24 мес. → 2,49%, пометка индивидуальная.
4. Калькулятор Б, 24 мес. → 2,99%.
5. Калькулятор А, 12 мес. → 1,99%, без пометки.

### Сценарий C. Смена базы без сброса исключений

1. База 24 мес. 2,99% → 2,79%. Режим 1 или 3.
2. Система показывает: без исключения на 24 мес. — 2 партнёра, с исключением — 1.
3. После сохранения: А = 2,49%, Б = 2,79%, база = 2,79%.
4. Старая заявка А на 24 мес. с 2,49% остаётся 2,49%.

### Сценарий D. Смена базы ко всем

1. Тот же ввод 2,99% → 2,79%, режим 2, второе подтверждение.
2. Исключение А на 24 мес. удалено.
3. А = 2,79% base, Б = 2,79% base.
4. Если у А было исключение на 36 мес., оно на месте.

### Сценарий E. Сброс исключения после смены базы

1. После сценария C у А исключение 2,49% при базе 2,79%.
2. Сброс 24 мес. с подтверждением.
3. А, 24 мес. → 2,79% base.

### Сценарий F. Деактивация

1. Программу деактивировали.
2. Назначения на месте, исключения на месте, админ их видит.
3. Партнёр не может сделать новый расчёт/заявку по ней.
4. Старые заявки читаются со снимком.
5. Активация возвращает программу в калькулятор с теми же исключениями.

### Сценарий G. Новый партнёр в справочнике

1. Программу когда-то назначили «всем».
2. Завели нового партнёра.
3. Он программу не видит, пока его не назначат отдельно.

### Сценарий H. Добавили срок 60 мес. в уже назначенную программу

1. Сохранили 60 мес. = 3,49%.
2. Все текущие назначенные партнёры сразу имеют 60 мес. по 3,49% base.
3. Исключений на 60 мес. нет.

### Сценарий I. Партнёр без прав

1. Партнёр открывает калькулятор — ставки только читаются.
2. Любая попытка записать исключение или базу от имени партнёра отвергается сервером.

---

## 17. Инварианты

Их нельзя нарушить ни экраном, ни обходным запросом.

1. Одна программа — одна запись программы, сколько бы партнёров ни назначили.
2. Назначение не порождает копию сроков.
3. Исключение существует только при наличии назначения и только на существующий срок программы.
4. На пару программа+срок ровно одна база.
5. На тройку программа+партнёр+срок не больше одного исключения.
6. Применяемая ставка для живого расчёта всегда вычисляется, а не читается из кэша партнёра.
7. Снимок заявки иммутабелен.
8. Неактивная программа не создаёт новые заявки.
9. Админ и суперадмин эквивалентны в этом функционале.
10. Партнёр не является автором ставки.
11. «Всем» не означает «всем будущим».
12. Программный счётчик «индивидуальные» считает партнёров с любым исключением; диалог смены базы по сроку T считает исключения только на T.

## 18. Ошибки, которые система должна уметь объяснить

| Ситуация | Смысл отказа |
| --- | --- |
| Пустое имя программы | Наименование обязательно |
| Имя уже есть | Название должно быть уникальным |
| Нет продуктов | Выберите хотя бы один продукт |
| Нет сроков | Добавьте хотя бы один срок |
| Два одинаковых срока | Один и тот же срок нельзя добавить дважды |
| Ставка отрицательная | Ставка не может быть отрицательной |
| Смена базы без выбора режима, если есть назначения | Нужно выбрать способ применения |
| Режим «ко всем» без второго подтверждения | Нужно подтвердить замену индивидуальных ставок |
| Смена продуктов при ненулевых назначениях без подтверждения | Нужно подтвердить последствия для партнёров |
| Сброс исключения без подтверждения | Нужно подтверждение |
| Исключение без назначения | Программа не назначена партнёру |
| Исключение на несуществующий срок | Срок отсутствует в программе |
| Калькулятор по чужому партнёру | Недостаточно прав |
| Калькулятор по неактивной программе | Неактивная программа не используется для новых заявок |
| Калькулятор без назначения | Программа не назначена партнёру |
| Управление программами без роли админ/суперадмин | Недостаточно прав |

Сообщения показывать человеку по-русски. Технический код ошибки можно иметь рядом, но логика отказа должна быть такой, как в таблице.

---

## 19. Вне объёма этой версии

Не делать, пока нет отдельного требования:

- снятие программы с партнёра;
- автоназначение программы всем новым партнёрам;
- разные сетки ставок внутри одной программы по продуктам;
- автоматический выбор «самой выгодной» программы;
- версионирование программы во времени помимо снимка заявки и журнала;
- согласование смены ставки несколькими людьми;
- физическое удаление программ из интерфейса;
- изменение формулы лизингового платежа.

Формула платежа остаётся как в текущем продукте. Этот функционал подставляет в неё только применяемую ставку.

## 20. Приёмка логики

Проверка считается пройденной, только если выполняются утверждения, а не «экран похож».

1. Создание программы не назначает никого.
2. После назначения число программ с этим именем равно 1 при любом числе партнёров.
3. У назначенного партнёра без исключений все сроки равны текущей базе.
4. Исключение на один срок не затрагивает другие сроки.
5. Партнёр без исключения всегда получает актуальную базу, даже если базу меняли после назначения.
6. Режим 1 и режим 3 не уничтожают исключения.
7. Режим 2 уничтожает исключения только по изменённым срокам и только после второго подтверждения.
8. Сброс исключения берёт **текущую** базу, не историческую.
9. Новая заявка содержит снимок; правки программы его не меняют.
10. Неактивная программа исключена из нового расчёта.
11. Новый партнёр после «назначить всем» в прошлом программу сам не получает.
12. Добавленный срок сразу виден всем уже назначенным.
13. Админ и суперадмин выполняют одни и те же операции.
14. Партнёр не может записать ставку.
15. Счётчики в списке программ считаются по наличию любого исключения; диалог смены базы — по исключению конкретного срока.
16. Пункт «Условия финансирования» в меню отсутствует.

Если реализация для удобства кэширует применяемую ставку у партнёра, кэш обязан либо отсутствовать, либо полностью совпадать с алгоритмом раздела 5 после каждого изменения базы, исключения, срока и назначения. Любое расхождение с вычислением «на лету» — дефект.
